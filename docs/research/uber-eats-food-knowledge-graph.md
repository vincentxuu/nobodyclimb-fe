## Part 1：原文整理

### 6.4.2 Uber Eats 的推薦系統（p.193）

- 由於 Uber Eats 了解每間餐廳所需的停車時間，因此可以提高派遣效率，讓系統能夠根據一天中的時間和交通狀態來優化派遣過程。

在能夠準確地掌握每個外送的進度過程後，Uber Eats 轉而優化他們的搜尋和推薦系統，目的是讓用戶在搜尋食物時，更精確地找到他們的心之所向。

#### 了解用戶需求

在建立整套搜尋系統之前，首先必須先清楚了解「用戶究竟在搜尋什麼」。用戶在訂購時的情境可能有以下幾種：

- 用戶明確知道自己要喝手搖飲料，因此直接搜尋相關店家並選購下訂。
- 用戶想要訂購午餐或晚餐，但是尚未決定要吃什麼。他們可能會有一個大致的方向，例如：想要吃亞洲菜、不想吃美式，但是尚未決定是日式或中式。
- 用戶可能已經有某個想吃的菜色，例如：烏龍麵，但最終卻選擇其他餐點，例如：拉麵。

這些情境展示了用戶的選擇會受到時間、飲食偏好和心情等多種因素影響。對人類而言，日式和中式、烏龍麵和拉麵都是相似的菜式，但是機器卻不一定能夠判斷之間的異同，因此如何讓機器理解菜式之間的相似性是一大考驗。

此外，Uber Eats 的搜尋系統和一般搜尋系統有很大的區別，因為他們主要使用於餐廳和食物的推薦，會面臨以下幾個挑戰：

- 一家餐廳可能主要提供某一種菜系，但是其菜單可能包含其他種類的食物，例如：一間韓式餐廳可能也會同時販售烏龍麵、拉麵等日式食物。
- 即使兩種菜餚的名字完全不同，實際上可能有相似的特徵，在搜尋時應該要存在足夠的關聯性，例如：清蒸檸檬魚和打拋豬肉都是泰式食物，很常同時被訂購，儘管名字毫無關聯。
- 由於地理位置的限制，有些餐廳或食物可能會無法搜尋到，例如：用戶搜尋「拉麵」，但是在他的送餐區域中卻沒有任何一間販售拉麵的餐廳。

### 建立食物知識圖譜（p.194）

在了解用戶的需求和使用情境後，為了幫助機器更精準地理解用戶需求，Uber Eats 決定使用在搜尋系統上很常見的圖譜（graph）技術，建立一個**食物知識圖譜（food knowledge graph）**，並嘗試透過**查詢理解（query understanding）**的技術，根據用戶輸入的「查詢」（query）來處理需求。另外，受到地區限制，用戶不一定每次都能夠搜尋到感興趣的食物，因此 Uber Eats 使用**查詢擴展（query expansion）**的技術，使得他們能夠在用戶搜尋時回傳更多的相似內容。

一般來說，「查詢理解」最常見的方法是使用自然語言處理技術，但是如同前文所述，當用戶的意圖不夠明確或是受到地理位置的限制時，僅仰賴自然語言處理技術是不足夠的，需要更深入理解食物之間的關聯。為此，Uber Eats 選擇採用「食物知識圖譜」的方式，將餐廳、菜式種類和菜單品項等內容作為**實體（entity）**，將這些實體作為圖譜中的**節點（node）**，再進而描述之間的關係。

#### 資料處理

Uber Eats 建立了一個資料流程，將各處蒐集來的資料經過以下步驟，最終轉換成圖譜：

1. 從各地蒐集的原始資料，會根據本體轉換成對應的實體關係。
2. Uber Eats 會進行資料清洗和篩選，以避免不同來源的資料重複。（p.195）
3. 圖譜建立完成，資料會被儲存成一種方便即時查詢的格式。

> **【說明】本體（ontology）**
>
> 在建立圖譜之前，通常會設計一個本體來描述圖譜中實體的類別、屬性和實體之間的關係。以 Uber Eats 的食物知識圖譜為例：
>
> - **實體**：圖譜中的節點，例如：麥當勞、烏龍麵、義式料理等。
> - **類別**：每個實體都會有一個對應的類別，例如：餐廳、菜式或餐點等。麥當勞是一個實體，其類別為「餐廳」；烏龍麵則是另一個實體，其類別為「餐點」；而義式料理這個實體的類別為「菜式」。
> - **屬性**：每個實體都會有相關的屬性，用以描述實體的特徵。例如：對餐廳而言，其屬性可能包括地址、評分或營業時間。
> - **關係**：在圖譜中會描述不同實體的關係。例如：可以用 `subCategoryOf` 描述「日式料理」為「亞洲菜」的子類別，或是用 `countryOfOrigin` 描述「壽司」是源自於「日本」。

**圖 6-30 食物知識圖譜的本體示意**（p.195）

```
亞洲菜 ──subCategoryOf──▶ 中式料理
亞洲菜 ──subCategoryOf──▶ 日式料理
日式料理 ──countryOfOrigin──▶ 壽司
日式料理 ──countryOfOrigin──▶ 烏龍麵
日式料理 ──countryOfOrigin──▶ 拉麵
麵 ──subCategoryOf──▶ 烏龍麵
麵 ──subCategoryOf──▶ 拉麵
```

#### 建立食物知識圖譜及優化

在建立食物知識圖譜時，對於實體的理解和標註是非常重要的，才能夠有效率地讓機器學習菜品、地區與國家之間的關係和差異。例如：當用戶輸入「亞洲菜」時，機器必須知道日式和中式都是亞洲菜的子類別。另外，當用戶輸入「拉麵」時，機器要知道「烏龍麵」、「蕎麥麵」和「日式料理」都是相關的字詞，因此線下的資料標註扮演著十分關鍵的角色，需要確保所有相關的餐廳、菜式和餐點都有被標註，才能夠在線上被用戶搜尋到。

### 冷啟動問題和零結果問題（p.196）

除了能夠讓機器更清楚地了解餐廳和餐點之間的關係以外，將這些資訊建立成圖譜還有另外一個好處，就是可以解決冷啟動問題和零結果（zero result）問題。舉例來說，如果用戶搜尋一間沒有和 Uber Eats 合作的餐廳，或是不在用戶可外送區域的餐廳，與其直接不回傳任何結果，不如利用圖譜的連結特性，推薦用戶其他類似的餐廳。此外，如果 Uber Eats 進軍一個新的城市，也不會因為缺乏用戶行為資料，造成無法推薦適合的餐廳，只要透過圖譜的資訊，就可以回傳和用戶搜尋文字相關的餐點與餐廳。

### 查詢擴展（p.196）

在一開始討論 Uber Eats 的用戶需求時，曾提過在食物和餐廳搜尋系統中會有一個潛在問題：「由於地區限制，當用戶輸入想要點購的食物時，他的所在地不一定有對應的餐廳和餐點」。例如：假設用戶搜尋「烏龍麵」，用戶的所在位置卻沒有任何販售烏龍麵的餐廳，在這種情境下，Uber Eats 希望能夠回傳與烏龍麵相近的食物，而非什麼內容都不回傳，為此他們使用「查詢擴展」（query expansion）這個方法，以優化使用者體驗。

> **【說明】查詢擴展**
>
> 查詢擴展是一個在搜尋系統中的常見方法，為了提高召回率（recall）和搜尋品質，會找尋和原本的查詢相關的字詞，例如：同義詞或改寫文句，並根據這些新增的字詞重新查詢，藉此找出更多相關內容。查詢擴展特別適合用在以下兩種情境：
>
> - 當用戶查詢的意圖不明確時，例如：用戶可能不確定自己想吃日式還是中式菜系，只知道自己想要吃亞洲菜。
> - 和搜尋字詞相關的查詢結果有限，例如：由於地區限制，用戶的所在地沒有販售拉麵的餐廳。

### query2vec 模型（p.197）

查詢擴展的關鍵是要能夠根據原始的查詢來找尋相似的查詢內容。常見的方法是比較在向量空間中兩個查詢的相似程度。為了計算查詢之間的相似程度，Uber Eats 利用用戶的搜尋行為資料，建立出 query2vec 模型。

以自然語言處理技術中 GloVe 演算法為靈感，Uber Eats 提出 query2vec 模型，以計算出每個查詢的嵌入。

> **【說明】GloVe 演算法**
>
> GloVe 的全名是「Global Vectors for Word Representation」，這是一個使用非監督學習（unsupervised learning）來學習字詞之間的關係，並產生代表每個字詞的嵌入。GloVe 在計算時，會參考整個文本中單詞的共現（co-occurrence）次數，有助於捕捉單詞之間的語意相似性。

Uber Eats 的 query2vec 模型是構築於 GloVe 的架構，其中有兩個重要概念：「字詞」（word）和「脈絡」（context）。

- **字詞**：在 query2vec 中，Uber Eats 將用戶在搜尋時輸入的整個查詢當作一個字詞。
- **脈絡**：在 query2vec 中，脈絡的定義是「如果兩個查詢最後會導致於同一間餐廳的訂單，代表這兩個查詢有相同脈絡」。

根據這個概念，若兩個查詢在同樣脈絡之下，則他們兩者在嵌入潛在空間（embedded latent space）會很接近，因此會有相似的嵌入。透過這個方式，Uber Eats 可以訓練出每個查詢的嵌入，並進一步運用在之後的機器學習模型之中。

**圖 6-31 query2vec 中查詢和脈絡之間的關係**

| 脈絡 | Queries | → 餐廳 |
|------|---------|--------|
| Context 1 | 火鍋、辣 | 麻辣火鍋店 |
| Context 2 | 辣、韓式料理 | 辣炒年糕店 |
| Context 3 | 韓式料理、烤肉 | 韓式烤肉店 |

## Part 2：對應到攀岩路線推薦

> 以下為把上述方法對照到 NobodyClimb 路線推薦情境的整理，非書籍原文。

### 2.1 使用者情境對照

| Uber Eats 情境 | 攀岩對應情境 |
|---------------|------------|
| 明確知道要喝手搖飲 → 直接搜尋店家 | 明確知道要爬哪條路線（如「龍洞校門口 5.10a 某條」）→ 直接搜尋 |
| 想吃亞洲菜但不確定日式或中式 | 想找「戶外運動攀 5.10 左右」但不確定去龍洞還是關子嶺 |
| 想吃烏龍麵最後點了拉麵 | 想爬 crimpy 直壁最後爬了同區的另一條相似路線 |

共同結論：**使用者的選擇受時間、偏好、當下狀態影響，且「相似」需要機器可判斷**。對人類而言 5.10a 與 5.10b、指力點與微把手是相近的，機器需要顯式建模。

### 2.2 攀岩路線知識圖譜（ontology 草案）

| 概念 | Uber Eats | NobodyClimb |
|------|-----------|-------------|
| 實體 entity | 餐廳、菜式、餐點 | 岩場（crag）、岩區（sector）、路線（route）、攀登風格（style） |
| 類別 category | 餐廳／菜式／餐點 | crag／sector／route／style／grade |
| 屬性 attribute | 地址、評分、營業時間 | 難度、長度、確保型式（bolt/trad/top-rope）、岩質、面向、接近時間、遮蔽 |
| 關係 relation | subCategoryOf、countryOfOrigin | locatedIn、sameSectorAs、similarStyleTo、adjacentGrade、requiresSkill |

示意：

```
運動攀登 ──subCategoryOf──▶ 先鋒攀登
龍洞 ──hasSector──▶ 校門口
校門口 ──hasRoute──▶ 某路線
某路線 ──gradeIs──▶ 5.10a
某路線 ──styleIs──▶ 指力點 / 垂直面
5.10a ──adjacentGrade──▶ 5.10b
```

### 2.3 三個可直接借用的機制

**① 知識圖譜補足語意相似**
單靠關鍵字或向量檢索無法知道「crimpy」和「小點」、「5.10a」和「5.10b」相關。用圖譜顯式標註 style / grade / 岩質關係，推薦時可沿邊擴散。

**② 查詢擴展（query expansion）解決地理限制**
使用者搜尋「多繩距 trad」但所在區域沒有 → 不要回傳空結果，改回傳圖譜上相鄰的路線（同岩場其他型式、鄰近難度、相似風格）。這正是 Uber Eats 「沒有烏龍麵就推薦相近餐點」的做法。

**③ 冷啟動 / 零結果**
- 新使用者無攀登紀錄 → 用圖譜（難度 + 風格 + 地區）而非協同過濾做推薦。
- 新岩場上線、無人留紀錄 → 靠圖譜屬性即可被搜尋與推薦到。

**④ route2vec（對應 query2vec）**
- 字詞 = 一次查詢（或一條路線）。
- 脈絡 = 「兩個查詢／兩條路線最終導向同一次攀登記錄或同一趟行程」→ 視為同脈絡。
- 用既有 ascent 紀錄訓練嵌入，同一天／同一趟被爬的路線嵌入會接近，可直接用於相似路線推薦。

資料來源：站上既有的攀登紀錄（ascents）、收藏、搜尋 log。

### 2.4 落地順序建議

1. **先做標註**：把路線的 style / grade / 岩質 / 型式補齊 — 書中強調「線下標註是關鍵，沒標到的線上就搜不到」。
2. **建立 ontology 與關係表**：先用關聯表存 route ↔ style ↔ grade，不必一開始就上圖資料庫。
3. **查詢擴展**：零結果時沿 adjacentGrade / similarStyleTo / sameSectorAs 擴展。
4. **route2vec**：等攀登紀錄量足夠後再訓練嵌入，補上行為訊號。
