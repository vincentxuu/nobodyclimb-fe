## 新增需求

### 需求：RAG 查詢執行
系統應透過結合向量搜尋結果與 LLM 生成來執行 RAG（檢索增強生成）查詢。

#### 場景：執行基礎 RAG 查詢
- **當** 使用者詢問「龍洞有什麼 5.10 的路線？」
- **則** 服務執行：1) 轉換查詢為 embedding，2) 搜尋 Vectorize，3) 取得 D1 文件，4) 生成 LLM 回應

#### 場景：回傳包含來源的答案
- **當** RAG 查詢成功完成
- **則** 回應包含：答案文字、包含 id/type/title/url/score 的來源陣列，以及 query_id

### 需求：向量相似度搜尋
系統應使用 cosine 相似度在 Vectorize 中搜尋 top-K 個最相似的文件。

#### 場景：使用預設限制搜尋
- **當** 查詢執行時未提供 limit 參數
- **則** 服務取得最相似的前 5 個文件

#### 場景：使用自訂限制搜尋
- **當** 查詢執行時 limit=10
- **則** 服務取得最相似的前 10 個文件

### 需求：Metadata 篩選
系統應支援依 metadata 欄位篩選向量搜尋結果：type、region、grade range、route_type。

#### 場景：依文件類型篩選
- **當** 搜尋執行時 filter type="route"
- **則** 只回傳路線文件

#### 場景：依等級範圍篩選
- **當** 搜尋執行時 grade_min=100 且 grade_max=110
- **則** 只回傳 grade_numeric 在 100-110 之間的路線

#### 場景：組合多個篩選條件
- **當** 搜尋執行時 type="route" 且 region="北部"
- **則** 只回傳北部地區的路線

### 需求：LLM 回應生成
系統應使用 `@cf/meta/llama-3.1-8b-instruct` 基於檢索到的上下文生成自然語言答案。

#### 場景：使用上下文生成回應
- **當** LLM 被呼叫時使用 system prompt 和檢索到的文件
- **則** 回應基於提供的上下文

#### 場景：處理沒有相關結果
- **當** 沒有文件符合查詢（所有分數低於門檻）
- **則** LLM 生成表示缺乏相關資訊的回應

### 需求：System prompt 設定
系統應使用可設定的 system prompt，指示 LLM 僅根據提供的資料以繁體中文回答。

#### 場景：套用 system prompt 規則
- **當** LLM 生成回應
- **則** 回應遵循規則：只使用提供的資料、使用繁體中文、簡潔扼要

### 需求：查詢結果快取
系統應使用 1 小時 TTL 將查詢結果快取在 KV 中，減少重複的 API 呼叫。

#### 場景：快取命中
- **當** 1 小時內進行相同查詢
- **則** 回傳快取的回應，不呼叫 embedding 或 LLM

#### 場景：快取未命中
- **當** 進行新查詢
- **則** 執行完整 RAG 流程並快取結果

#### 場景：快取鍵生成
- **當** 處理查詢
- **則** 從查詢雜湊生成快取鍵：`ai:ask:{hash(query)}`

### 需求：查詢記錄
系統應將所有查詢記錄到 ai_query_logs 表格，用於分析和改進。

#### 場景：記錄成功查詢
- **當** RAG 查詢完成
- **則** 建立包含以下內容的日誌記錄：query、response、sources、latency_ms、user_id（如已驗證）

#### 場景：記錄沒有使用者的查詢
- **當** 匿名使用者進行查詢
- **則** 日誌記錄的 user_id 為 null

### 需求：純語義搜尋
系統應支援不使用 LLM 生成的純向量搜尋，用於輕量級搜尋情境。

#### 場景：執行僅搜尋查詢
- **當** 呼叫搜尋端點
- **則** 服務回傳符合的文件，不進行 LLM 處理

#### 場景：搜尋回傳評分結果
- **當** 搜尋完成
- **則** 每個結果包含來自 Vectorize 的相似度分數

### 需求：來源 URL 生成
系統應為每種來源類型（route、crag、video）生成適當的 URL。

#### 場景：生成路線 URL
- **當** 來源是路線文件
- **則** URL 為 `/crags/{crag_id}/routes/{source_id}`

#### 場景：生成影片 URL
- **當** 來源是包含 youtube_id 的影片文件
- **則** URL 為 `https://youtube.com/watch?v={youtube_id}`

### 需求：最低分數門檻
系統應過濾掉低於可設定最低相似度分數（預設 0.5）的結果。

#### 場景：過濾低分結果
- **當** 向量搜尋回傳分數為 [0.9, 0.7, 0.4, 0.3] 的結果
- **則** 只包含分數 >= 0.5 的結果（前 2 個）

### 需求：自動位置過濾（NLP）
系統應從查詢文字中自動偵測並套用位置相關的 metadata 過濾，無需使用者明確指定。

#### 場景：偵測區域名稱（最高優先）
- **當** 查詢包含如「校門口」「鐘塔」等已知區域名稱
- **則** 自動過濾 `area_id` 並強制 `type=route`

#### 場景：偵測岩場名稱
- **當** 查詢包含如「龍洞」「墾丁」等已知岩場名稱
- **則** 自動過濾 `crag_id`

#### 場景：偵測地區名稱
- **當** 查詢包含如「花蓮」「北部」等地區關鍵字
- **則** 自動過濾 `region`

**實作**：`extractLocationFilter(query)` 依優先序查詢 D1（區域 → 岩場 → 地區）

### 需求：自動難度過濾（NLP）
系統應從查詢文字中自動偵測 YDS 難度，並轉為 grade_numeric 範圍過濾。

#### 場景：偵測完整難度（含子等級）
- **當** 查詢含「5.11b」
- **則** 過濾 `grade_numeric = 111`（精確符合）

#### 場景：偵測大等級（無子等級）
- **當** 查詢含「5.11」
- **則** 過濾 `grade_numeric` 在 110-113 之間（含 a-d）

**實作**：`extractGradeFilter(query)` 使用正則 `/5\.(\d+)([a-d])?/i`

### 需求：相似路線意圖偵測
系統應偵測使用者詢問「推薦相似路線」的意圖，並以被提及路線的岩場 + 難度範圍做精準過濾。

#### 場景：相似路線查詢
- **當** 查詢含「推薦和 XXX 相似的路線」或類似意圖關鍵字
- **則** 自動擷取被提及路線的岩場與難度，以同大等級（如 5.11a-d）+ 下一大等級起始（如 5.12a）做範圍過濾

**理由**：YDS 難度跳躍問題（5.11d→5.12a 相差 7），±3 無法跨越等級邊界，需動態計算範圍

**實作**：`hasSimilarRouteIntent(query)` + `extractRouteReference(query)` 配合大等級公式
