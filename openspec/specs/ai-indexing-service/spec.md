## 新增需求

### 需求：路線文件索引
系統應將路線記錄轉換為可搜尋的文件，結構化文字格式包含名稱、等級、岩場、類型和描述。

#### 場景：索引單一路線
- **當** 索引服務處理一筆路線記錄
- **則** 服務建立格式為「路線名稱：{name}\n所屬岩場：{crag}\n難度等級：{grade}\n...」的文件

#### 場景：索引缺少欄位的路線
- **當** 路線的描述或等級為 null
- **則** 文件使用「未知」或「無描述」作為佔位文字

### 需求：岩場文件索引
系統應將岩場記錄轉換為可搜尋的文件，包含位置、攀登類型、季節和描述。

#### 場景：索引包含所有欄位的岩場
- **當** 索引服務處理一筆岩場記錄
- **則** 服務建立包含地區、岩石類型、攀登類型和最佳季節的文件

#### 場景：索引包含 JSON 陣列欄位的岩場
- **當** 岩場的 climbing_types 為 JSON 陣列 ["sport", "trad"]
- **則** 文件將其格式化為「運動攀登、傳統攀登」

### 需求：雙重儲存架構
系統應將 embeddings 儲存在 Vectorize，將完整文件文字儲存在 D1 ai_documents 表格。

#### 場景：儲存包含 embedding 的文件
- **當** 文件被索引
- **則** embedding 向量與 metadata 一起儲存在 Vectorize，且完整文字儲存在 D1

#### 場景：連結 Vectorize 和 D1 記錄
- **當** 文件被儲存
- **則** D1 記錄包含與 Vectorize 向量 ID 相符的 embedding_id

### 需求：Vectorize metadata 索引
系統應在 Vectorize 向量中包含可篩選的 metadata 欄位：type、grade_numeric、crag_id、region、route_type。

#### 場景：儲存路線 metadata
- **當** 路線文件被索引
- **則** Vectorize 向量包含 metadata：{ type: "route", grade_numeric: 100, crag_id: "xxx", route_type: "sport" }

#### 場景：等級數值轉換
- **當** 路線等級為「5.10a」
- **則** metadata 包含 grade_numeric: 100（基數 10 × 10 + 後綴索引）

### 需求：批次索引
系統應支援批次索引多個文件，自動分割以符合 Vectorize 限制（每次 upsert 最多 1000 個向量）。

#### 場景：批次索引 500 條路線
- **當** 服務索引 500 條路線
- **則** 服務在單次 Vectorize upsert 呼叫中處理

#### 場景：批次索引 1500 條路線
- **當** 服務索引 1500 條路線
- **則** 服務分割為 2 次 Vectorize upsert 呼叫（1000 + 500）

### 需求：完整重建索引能力
系統應支援依類型（route、crag、video）或所有文件的完整重建索引。

#### 場景：重建所有路線索引
- **當** 管理員觸發 type="route" 的重建索引
- **則** 服務刪除所有現有路線向量和文件，然後從來源資料重建索引

#### 場景：重建所有文件索引
- **當** 管理員觸發 type="all" 的重建索引
- **則** 服務依序重建路線、岩場和影片的索引

### 需求：文件 ID 生成
系統應使用一致的 ID 生成工具為每個文件生成唯一 ID。

#### 場景：生成文件 ID
- **當** 建立新文件
- **則** 生成唯一 ID（例如 nanoid 或 UUID 格式）

#### 場景：相同來源產生相同結構
- **當** 重新索引相同路線
- **則** 生成新的文件 ID（先刪除舊記錄）
